# Roadmap: factions, draft and the new roster

Status: plan, November 2026. Nothing here is built yet. Done before this: the
data-driven roster, the character kit, skill animations, the new-unit workflow,
the warrior redesign, legs matching ground speed and the unit lab.

The goal: the game set on the Dnipro road (`design/SETTING.md`), three factions
of their own units, a draft before each battle, and units that level up to
three abilities. Units will change the most from now on, so first the code is
made safe for several sessions working on different units at once.

```
Phase 0  Refactor for parallel unit work   (one session at a time: shared core)
Phase 1  Gameplay flow: levels, faction pick, draft
Phase 2  Unit plan review                   ── HARD STOP: the user reviews design/ROSTER-PLAN.md
Phase 3  Shared effects and behaviours      (one session: shared core)
Phase 4  Units, one session per unit        (parallel)
Phase 5  Setting: maps, names, UI, retire the old three
```

Phases 0 and 1 can overlap: Phase 0 is mostly `sim/` and data files, Phase 1
mostly `server/run`, `proto/`, `web/src/store.ts` and the UI. Steps that touch
the same files go one after another.

## Phase 0: refactor for parallel unit work

What happens today when two sessions each add a unit, measured on the code:

| Hotspot | Why two unit sessions collide |
|---|---|
| `sim/roster.go` `var Roster = []UnitDef{…}` and `sim/data.go` `Class` consts | Both append to the same line; both take the "next" id. |
| `sim/data.go` `Skill` enum ("next free id") | Both take the same new skill id; `ValidateRoster` catches it only after merge. |
| `sim/roster.go` `EffectKind` enum, `effectNames`, `checkEffect`; `sim/unit.go` `newUnit` and `think` | A new kind of ability edits the same enum, arrays and switches. |
| `sim/battle.go` `Version` | Every rule change bumps the same constant. |
| `sim/testdata/golden.json` | One file regenerated by every rule change: always conflicts. |
| `docs/balance-report.md` | One generated file, rewritten by every balance run. |
| `web/src/units/looks.json` | All units' looks, clips and builds in one JSON. |
| `web/src/units/clips.json` (generated) | One bundle regenerated from all looks. |
| `web/src/scene/fx.json` | All effect presets in one JSON. |
| `tools/blender/bake_parts.py` (item poses, `CLOTH`), `parts.json` | Per-item data inside shared code; one generated manifest. |
| `docs/GAME_CONCEPT.md` §4 and §10, `CLAUDE.md` | Per-unit stats and skill tables in shared docs. |

Already good: the web client, server and UI never name units (everything comes
from `wasm data()` and the looks), and the new-unit workflow keeps briefs and
previews per unit.

### Steps

Each step is one PR. Steps 0.1–0.3 change no outcomes: the golden replays must
stay identical, which is how the refactor is checked.

**0.1 Split shared data files per unit** (no rule change) — done
- As built: looks in `web/src/units/looks/<unit>.json` + `_shared.json` (builds
  and clips used by several units); clip bundles `web/public/assets/clips/<look
  file>.json`, written by `ual_clips.py` byte for byte as before; presets in
  `scene/fx/*.json`; items in `tools/blender/items/*.json` (the bake reproduces
  `parts.json` exactly); golden replays one file per case, with a case per
  roster entry generated automatically. `pnpm balance:unit` prints to the
  terminal, so it never conflicted; the generated per-unit README was dropped
  (the briefs and roster files cover it).

Original plan:
- Looks: `web/src/units/looks/<unit>.json` per unit, plus `looks/_clips.json` and
  `looks/_builds.json` for the shared parts; `looks.ts` merges them (Vite glob
  import). `wasm/looks_test.go` reads the folder.
- Clips: one bundle per unit (`clips/<unit>.json`), built by `ual_clips.py`,
  loaded for the units in the battle. Shared clips go in `clips/_common.json`.
  Budgets stay per bundle and in total.
- Effects: `scene/fx/<name>.json` per preset group; each unit's own presets in
  `fx/<unit>.json`.
- Parts: item poses and cloth specs move out of `bake_parts.py` into
  `design/units/<unit>/items.json` (or `tools/blender/items/<unit>.json`), which
  the bake reads; the bake writes `parts.json` sorted, so re-baking two branches
  gives the same file.
- Golden replays: `sim/testdata/golden/<case>.json`, one file per case; unit cases
  named after the unit.
- Balance: `pnpm balance:unit <name>` writes `docs/balance/<unit>.md`; the full
  report (`pnpm balance`) is only rewritten in its own PR.
- Docs: the per-unit tables in `GAME_CONCEPT.md` move to generated
  `design/units/<unit>/README.md` (from the roster), and the concept doc links
  to them.

**0.2 Ids that can't collide** (rule change: version bump, golden update) — done
- As built: `sim/ids.go` holds unit and effect kind ids; unit files register
  themselves; abilities are numbered per unit (`WarriorDash` = 4, `MageFrost`
  = 1, ...) and the proto carries plain numbers (the `Skill` enum is gone).
  `sim.Version` 0.5.0; every golden outcome is unchanged (only the version
  field), and the roster baseline only renumbers abilities.
- Unit ids stay dense (the client indexes units by id). So no gaps appear while
  units are built in parallel, Phase 3 creates all nine new units at once as
  valid placeholder entries with placeholder looks; Phase 4 sessions then only
  fill in their own unit's files and never allocate ids.

Original plan:
- Unit ids: one file, `sim/ids.go`, lists every unit id, planned ones included,
  allocated in planning PRs only (Phase 2 allocates the nine new units at once).
  A unit file registers itself (`func init() { register(huskarlDef) }`); the
  roster is built sorted by id, so no shared slice to append to.
- Skill ids: local to the unit. A unit's abilities are numbered 1..N within
  its roster entry, and the wire carries (unit, ability index). The global
  `Skill` enum and "same id means the same thing" rule go away. `UnitSpec.skills`
  becomes ability indexes (the proto enum stays only for old replays, or is
  dropped with a version bump, since there are no players to keep).
- Effect kind ids: explicit numbers in `sim/ids.go`, allocated like unit ids.

**0.3 Effects as plug-ins** (no outcome change) — done
- As built: `sim/effects.go` (registry, hooks, loadout) and one file per kind
  (`effect_stat.go`, `effect_finisher.go`, `effect_slow.go`, `effect_splash.go`,
  `effect_gapcloser.go`, `effect_escape.go`, `effect_overcover.go`), each with
  its own check. Cooldowns live on the learned effect, not the unit. Every
  golden replay is unchanged, under the same version.

Original plan:
- Each effect kind lives in its own file, `sim/effect_<name>.go`, implementing a
  small interface: check its numbers, fold into the unit's loadout, and hooks the
  battle calls in a fixed order (before acting, on hit, on being hit, on death of
  a nearby unit, each tick for auras). The registry is a slice sorted by kind id,
  never a map, so the sim stays deterministic.
- The seven existing kinds move there; `newUnit` and `think` call hooks instead
  of switches.
- After this, a new kind of ability is one new file plus its id: no shared edits.

**0.4 Behaviour as data** (no outcome change) — done
- As built: `Temperament` in each roster entry (`sim/temperament.go`) with a
  target rule and an engage rule, both plug-ins with ids in `ids.go`
  (`target_nearest.go`, `engage_charge.go`), and `Kite` (moved from Stats).
  Effects get a `temper` hook, so abilities can change temperament (review
  answer 4). `wasm data()` publishes each unit's temperament. Today's three
  units are nearest + charge (archer also kites); every golden replay is
  unchanged. The other fields from the roster plan (leash, keep distance, fall
  back, stay near) and the other rules (line, hold, wounded, ranged first,
  strongest, focus, protect) are Phase 3 work, each a field or a rule file.

Original plan:
- A unit's temperament becomes data in its roster entry (see "Behaviour" in
  `design/ROSTER-PLAN.md`): how eagerly it engages, how far it chases, the
  distance it keeps, when it falls back, whom it targets.
- `think` reads the profile; today's behaviours become three profiles
  (warrior: charge the nearest; archer: kite; mage: hold), and the golden
  replays prove nothing changed.

**0.5 Version and workflow** — done
- As built: `sim.Version` = `RulesVersion` + roster fingerprint, set as units
  register; golden cases record `VersionFor` the units they use, so `-update`
  rewrites only the cases a change touches (no `-case` flag needed). The
  parallel workflow is in `CLAUDE.md` ("Parallel unit work"); the local
  `/new-unit` skill follows it.

Original plan:
- `sim.Version` gets a roster fingerprint: `Version = "0.5.0+" + hash(roster)`,
  so changing a unit's numbers changes the version without editing a shared
  constant. Manual bumps are only for rule code.
- Per-unit golden cases update only their own files (`-update -case <unit>`).
- The `/new-unit` skill and `CLAUDE.md` describe the parallel workflow:
  - one session per unit, in its own worktree and branch;
  - it touches only `sim/unit_<name>.go`, `design/units/<name>/`,
    `looks/<name>.json`, `clips/<name>.json`, `fx/<name>.json`, its golden case
    and its balance report;
  - a unit needing a new effect kind or behaviour field asks for it as a
    separate shared-core PR first (Phase 3 does the planned ones up front);
  - before the PR: rebase on main, `pnpm test`, `pnpm balance:unit`.

## Phase 1: gameplay flow

### 1.1 Levels: three abilities at most (rule change)

Done (OpenSpec `unit-levels`): `sim.MaxLevel` = 3, inputs need 1 to 3
abilities per unit, Red's units start with one random ability and its count
means abilities above level 1, picks stop at level 3, `RulesVersion` 0.6.0.
Until the draft (1.3), the client gives each recruit a random level-1 ability
that stays the same for the run, match and slot. The balance lab follows the
new rules; `pnpm balance` (the full report) has not been rerun yet.

- Each unit type has a pool of **five abilities**. A unit knows at most **three**.
- **Level 1** (a new recruit): one ability, picked during the draft (random if
  the timer runs out).
- **Level 2** and **level 3**: one more ability after each won battle, picked on
  the Victory screen as today.
- Level = number of abilities, shown as ★ like today.
- Red: its recruits also start at level 1 with a random ability; the Red scaling
  rule ("Red gets as many abilities as you") counts levels instead.
- `MaxSkills` 5 → 3 learned (the roster still lists 5); server `PickSkills`
  and `army.go` validation follow. Balance lab rerun, numbers retuned.

### 1.2 Faction pick (at the start of a run)

Done (OpenSpec `faction-pick`): factions are sim data (Classic for now);
`BattleInput.blue_faction`, Blue's units checked against it; Red's faction is
drawn from the map seed (mirrors allowed) and Red's army from it; runs and
battles store the faction (migration 0006); a faction screen opens every new
run, with Rus, Varangians and Romans shown as coming soon. `RulesVersion`
0.7.0, outcomes unchanged. Since Red's army is fixed by the seed, the draft
(1.3) can reveal Red's picks turn by turn in the client and the server only
checks the locked army: no `DraftPick` RPC is needed in single player.

- New first screen of a run: the three factions side by side, each with its
  lore (from `design/SETTING.md`), colours, and its units with their roles and
  abilities.
- The pick is part of the run (stored by the server, sent with each battle).
- Factions are data: `sim/factions.go` (or one file per faction) lists a faction's
  units; `wasm data()` publishes them. Red's faction is a seeded random pick
  each battle; mirrors are allowed.
- Until the new units exist, a "Classic" faction holds today's warrior, archer
  and mage, so the flow can ship before the roster.

### 1.3 Draft (before every battle)

Done (OpenSpec `draft`): the battle starts first (its map seed fixes Red's
faction, army, the coin flip and Red's reveal order: `sim.Draft`, wasm
`draft()`), then the draft runs in the client (`web/src/draft.ts`,
`ui/Draft.tsx`) and the drafted army goes to deployment; the army picker is
gone. The server only checks the locked army (no `DraftPick` RPC). Deploy
window 3 minutes. A reload mid-draft drafts the same battle again.

Original plan:

- A coin flip decides who picks first. Order of picks, five units each:
  **first 1 · second 2 · first 2 · second 2 · first 2 · second 1**.
- **15 seconds per turn.** If the time runs out, the remaining picks of that
  turn are random.
- Each pick is a unit type from your faction and its level-1 ability. Both
  sides see each other's picks as they happen (that is the point of the order:
  you answer what the other side drafted).
- Red is the second player for now: the server makes Red's picks from the
  battle's seed (counter-picking rules to be decided; the balance lab found
  random Red armies fair).
- Veterans: your surviving veterans fill your first picks automatically (at
  their level, with their abilities); you draft only the empty slots, in the
  same turn order. If all five survived, there is nothing to draft.
- Server: the draft is part of the battle's state (`StartBattle` opens the draft,
  a new `DraftPick` RPC records picks in order, `LockDeployment` checks the army
  equals the draft). The server checks the order and the pool; the 15 s timer
  is the client's job (single player).
- Client: a new `drafting` phase between `starting` and `deploying` in
  `store.ts`, and a draft screen with both sides' picks, the turn, the timer and
  the pool.
- Then deployment and the fight as today.

### Match flow after Phase 1

```
New run ─► Faction pick ─► Draft (1-2-2-2-2-1, 15 s/turn, level-1 abilities)
          ─► Deploy (15 s) ─► Fight ─► Win: survivors pick an ability (up to level 3)
                                       └► next battle: Draft again
                                 └─► Loss: run over, scoreboard
```

## Phase 3: shared effects and behaviours (one session)

Progress: 3.1 temperament done (OpenSpec `temperaments`: target rules wounded,
ranged first, strongest, focus, protect; engage rules line and hold; trigger,
leash, keep, fall back, stay near). 3.2 effect kinds done (OpenSpec `effect-kinds`: per-tick
modifiers, new hook points, traits, and 15 kinds with ids 8–22). 3.3 done
(OpenSpec `roster-placeholders`): unit ids 3–11 and faction ids 2–4
allocated; the nine units exist with the roster plan's stats, abilities and
temperaments, and borrowed looks (`ui.placeholder`); their factions aren't
`Playable` yet, so players can't pick them and Red never draws them (classic
battles unchanged; each new unit has its own golden case). The balance lab
mixes any units through a lab-only faction.

Notes for Phase 4:
- The new-unit balance bands assume a unit that fights on its own. A support
  unit like the huslyar fails "5 against 5" by design (0% in a first run):
  its session should propose bands that measure it inside an army.
- Shield wall (druzhynnyk) applies against ranged attacks only; the plan said
  "while standing" too (an effect has one condition).

Once the plan is approved, one session adds every new effect kind and behaviour
field the nine units need (each a file from step 0.3, each with rules tests and
lab presets), and allocates the nine unit ids and the effect ids. Units can then
be built without touching shared code.

## Phase 4: units (parallel, one session per unit)

Progress: **Kyivan Rus done and playable** (druzhynnyk #64, strilets #66,
huslyar #65, guard and brace effects #63, faction made playable after them).
Red now draws Classic or Rus. Next: Varangians, then Romans, one faction at a
time.

Each unit goes through `/new-unit`: brief, design checkpoint with the user,
roster file, look, golden case, balance band, previews, PR. Suggested waves,
so each faction is playable early:

1. The three melee units (druzhynnyk, huskarl, skoutatos).
2. The three ranged units (strilets, bowman, toxotes).
3. The three special units (huslyar, völva, siphonarios).

Factions become selectable as soon as they have all three units.

## Phase 5: setting

Maps that fit the setting (river banks, portages, forest edges, Balkan hills),
names and texts in the UI, run names, faction banners, then the Classic faction
is retired.

## Decisions

Decided (November 2026):
1. **Draft pool:** your own faction's unit types, duplicates allowed.
2. **Veterans:** surviving veterans are picked automatically; the draft fills
   the empty slots only.
3. **Red's faction:** seeded random each battle, mirrors allowed.
4. **Old units:** a temporary "Classic" faction (warrior, archer, mage) so the
   new flow ships early; retired once all three new factions are playable.

Open:
5. Is the second drafter always Red (single player)? The draft is built so a
   human could take Red's seat later (PvP), but nothing is planned for that.
6. ~~The review questions in `design/ROSTER-PLAN.md`~~: answered there (three types per faction for now, the huslyar weak alone, no effect cut, abilities may change temperament).
